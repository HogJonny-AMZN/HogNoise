### The SPIR-V on lavapipe: the plan
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)

The owner asked what lavapipe is, then said "Do it. PyPI isn't a priority yet". [The plan](../../superpowers/plans/2026-11-27-the-emitted-spirv-on-lavapipe.md)
for the CI proof's third pull request is Proposed. It was trial-run first, and its code is pushed as
`trial/spirv-on-lavapipe`, one commit per task, so each task names the commit it takes (its decision L1). (b) had
left open whether a Vulkan back end joins `hlsl_host.cpp`. The frame code turned out to have no D3D in it, so it
moved to `hosts/frames.h` and `hosts.harness`, and the Vulkan harness is a file of its own, built on Linux.

In a `ubuntu:26.04` container, CI's release with Mesa 26.0.8, lavapipe ran `noise.spv` and passed every hog case within
`wgpu.json` unmodified. It passed both controls and all eleven frame refusals, and four mutants of the harness each
failed. The HLSL hosts still passed on WARP. Two findings from the trial changed the branch:

- **A commit that dropped tests.** The first split moved the frame refusals out of `test_hlsl.py` one commit before
  they arrived in `test_frames.py`. That green commit had eleven fewer tests, and its pass count did not show it:
  only comparing the tests each commit collects did. The refusals now move in one commit.
- **A hang.** The first `make check` stopped at 98% and sat for 16 hours: every worker idle, the controller waiting,
  two cached `hlsl_host.exe` still open. Five runs since have passed, and the cause is not known. The plan names it
  under *Not covered*, and its gate step runs under `timeout`.

The handoff records "PyPI isn't a priority yet".

### The SPIR-V on lavapipe: built
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)

The owner merged [PR #64](https://github.com/HogJonny-AMZN/HogNoise/pull/64) (`2792a39`, 23:30 UTC), which accepts the
plan, and the build is [PR #65](https://github.com/HogJonny-AMZN/HogNoise/pull/65). Each task took its files from the
trial commit the plan names, and each was run again: WARP gave Task 1's 77 and Task 2's 82 passes, and Task 3 its two
planned collection errors. The tests collected at Task 2 were compared with Task 1's: none was lost, and one was split
into two, for the source and for `frames.h`. After Tasks 4 and 5, `apps/`, `.gitignore` and `.github/` are the same git
trees as the trial's, so the Linux run in the trial's container and its four mutants apply to this code unchanged.
They were not repeated locally.

CI ran the `spirv-vulkan` job for the first time, on the draft. It passed in 47 s, with 79 passed and 47 skipped, the
trial's numbers. `vulkaninfo` named `llvmpipe (LLVM 21.1.8, 256 bits)`, a CPU device on Mesa 26.0.8, and every hog
case passed on it within `wgpu.json` unmodified. `make check` passed 9 of 9 under `timeout 900`, with 3,377 passed and
136 skipped. It did not hang.

The review scored error handling 5. Its worst finding was older than this pull request: the harness's request check,
on main in `hlsl_host.cpp` and now in `frames.h`, never looked at the workgroups. 200 points dispatched as 1 x 1 came
back as status 0, with 136 zeros. The check now requires exactly the README's dispatch, and a mutant that takes it out
fails three tests. The other fixes:

- A Vulkan lookup that fails is now an error, not "no device".
- Five refusals had no test, and now do, among them the "is gone" path, made deterministic by size.
- A harness that cannot start is reported, not leaked.

The first mutant of the workgroup check did not build at `/WX`, so its tests skipped: a dead mutant, caught by reading
its count and not assuming it. After the fixes, lavapipe passed 88 in CI and the gate 3,386.
