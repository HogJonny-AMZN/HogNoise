### The DCC hosts
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)

HogHydra's session asked whether HogNoise would lock to the shared versions the owner's repositories now share
(LargeWorlds owns [the table](https://github.com/HogJonny-AMZN/LargeWorlds/blob/main/Docs/knowledge/shared-dependency-versions.md)).
The owner answered for HogNoise: it supports a range, and it must import in every supported DCC host on that host's own
Python and numpy. Their host list, and the versions read, are in [the DCC hosts](../../standards/compatibility-matrix-project.md):
Maya 2026, Houdini 21 and Unreal 5.8 at Python 3.11 with numpy 1.26.4, Blender 5.2 at 3.13 with numpy 2.3.4. HogHydra read
Maya, Blender and Marmoset inside each host through HogShade's BATS. This session read Houdini and Unreal from their install
files. Marmoset Toolbag 4 runs Python 3.9.4 with no numpy; the owner would move to Toolbag 5 before solving for it.

Two facts set what was built. The numpy floor was once raised to 2.x and that "wasn't the right direction"; the
[numpy 2 row](../../plan/board/2026-11-15-numpy-2-modernisation.md) already held the owner's 2026-11-15 answer, a 2.5+ path
beside the 1.26 one, never instead. And Dependabot rewrites declared requirements, not only the lock: it raised
`uv-build`'s floor twice ([PR #28](https://github.com/HogJonny-AMZN/HogNoise/pull/28),
[PR #47](https://github.com/HogJonny-AMZN/HogNoise/pull/47)). So Dependabot is held to the lock
(`versioning-strategy: lockfile-only`, which its schema accepts for uv), and `test_dcc_host_floors.py` refuses a raised
floor or a cap with the reason in its message: mutated to numpy 2.0, to a cap below 2.6 and to Python 3.12, it failed each
time, one test each. The floor leg is named for the three hosts it stands for, and Blender 5.2 has its own.

The fresh-sample bounds' plan merged ([PR #56](https://github.com/HogJonny-AMZN/HogNoise/pull/56)); the owner's "fix up and
then do both" set it Accepted here and the row In progress, and its build follows in its own pull request.

### The HLSL runs on WARP
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)

On the owner's "Go", [PR #59](https://github.com/HogJonny-AMZN/HogNoise/pull/59) builds [the HLSL plan](../../superpowers/plans/2026-11-23-the-emitted-hlsl-on-warp.md)
from its own text, task by task; the harness and its build script were extracted from the plan's blocks by a script,
so they are the trial's bytes. The one thing that had moved since the trial was the tolerance file, now format 2, and
both hosts pass it unmodified: 24 passed and 2 skipped (bit for bit is `spirv-naga`'s claim alone). CI's runner has
Visual Studio 2026 (folder `18`), which `build.bat` probes first; the `hlsl` job took 1 min 42 s. Each mutant failed
(two bindings swapped, one per API, and the y row of workgroups dropped), and the job told another target failed on
`HostTargetError` for both hosts, then passed again on the revert.

Two slips, neither pushed: a Task 2 commit made with `--no-verify` (its hook then run by hand on that tree, all 8
stages passing), and a `git revert` that refused a dirty tree while the next commit went on, so the revert was made by
hand. `llms.txt` and the README's lead sentence had said no host ran the shaders since
[PR #49](https://github.com/HogJonny-AMZN/HogNoise/pull/49); fixed with Task 6.

Copilot's review found two holes the deliberate review's fixes had left. The harness checked a request's sizes but
not its entry point's shape, so `warp_points_3d` asked for one float per point, or `sample_grid` sent no `Grid`, came
back status 0 with output that looked valid; it now checks the width, the axes and `Grid` against the README per
entry point, and refuses an init frame naming an entry point the README does not list. And `Timer.cancel` cannot stop
a watchdog callback already running, which could then kill the harness during the next request; the exchange now
joins it. Each of the 7 new tests failed against the code before its fix; with the fixes, 44 passed and 2 skipped.

CI on that commit failed once, on Linux, in the truncated-reply test from the deliberate review's round. The stand-in
harnesses answered init without reading it, so their `read(4)` read the init frame's `HNH1`, not the request; one
that then exited could break the pipe while Python was still writing, which is the "is gone" path, not the "stopped"
one the test names. They now read the init frame and the whole request before they answer. Making only the request
read whole hung the run on the unread init frame, which is how the first cause showed.

### The buffer limit, probed and planned
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)

[PR #59](https://github.com/HogJonny-AMZN/HogNoise/pull/59) merged (`3a83792`). On the owner's "Sure", [the buffer
limit's row](../../plan/board/2026-11-21-a-call-past-the-devices-buffer-limit.md) started with its probe, from a
worktree at `3a83792`. Every adapter on the 5090 machine binds at most 2,147,483,644 bytes: the 5090 on Vulkan, D3D12
and OpenGL, and WARP. One point past it, on WARP and on the 5090's Vulkan, for an axis past the limit and for
`warp_points`' output past it, wgpu raised its own `GPUValidationError` within 2.3 s, after uploading the axes, and a
small call then ran: no wrong answer and no crash. Its message is in its own terms (a buffer size on D3D12, a binding
number on Vulkan) and names neither the argument nor the most a call may take.

Offered three options (refuse before any upload, split into chunks, or document wgpu's error), the owner chose the
refusal ("Yes"). [Its plan](../../superpowers/plans/2026-11-25-a-call-past-the-buffer-limit.md) was trial-run in task
order: the tests fail on `main` (1 failed, 7 errors) and pass with the check (8 passed, on WARP and the 5090's Vulkan);
each of three mutants fails its tests. A first form of the tests built a second device with WebGPU's default limits and
ran a call at its limit on WARP, which cost about 2 minutes, so the standing tests lower the limit on the process's own
device instead, and that run is kept as trial evidence.

Copilot's review of the plan found the one upload outside `run`: `sample_grid` made its `Grid` uniform before calling
it, so a grid past the limit uploaded 48 bytes before the refusal, and the tests' sentinel stopped only `storage`. The
plan now has `run` take the packed bytes and upload them after the check (D7), and the fixture makes its sampler first,
then stops both kinds of upload. Trial-run again: the new tests failed on exactly that case against the first trial's
code, and with the change the whole GPU test file passes on the 5090's Vulkan and on WARP.
