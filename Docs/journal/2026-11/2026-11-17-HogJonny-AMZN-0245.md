### Stage 3's plan: the naga it pins was measured first
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)
**Board:** [`2026-11-01-gpu-fast-track`](../../plan/board/2026-11-01-gpu-fast-track.md)

The spec left one question for the plan's first task: whether the naga that `wgpu` runs (29) writes what the spec
measured with 30.0.1. It was cheap to answer before writing the plan rather than after, so the plan rests on it. The
first surprise: there is no naga-cli 29.0.1, the version inside `wgpu`; the command line skips from 29.0.0 to 29.0.2.
Built into the scratchpad with `--locked`, 29.0.2 links naga 29.0.2 and writes every file with no error, the same HLSL
registers, the same GLSL names and no padding, and both of Microsoft's compilers take every entry point. What differs
from 30 is naga's numbering of temporaries and one helper function. So the plan pins 29.0.2.

The second came from running the emitter's binding parser over that output before committing it (ledger P-12): a GLSL
variable is the member of its block, not a name after it, and the output buffer's block is named differently in each
entry point. A host binding GLSL by name needs the block per entry point, so the manifest records it that way.

The plan moves the tools into an app in its own pull request first, then builds the emitter, the `hog_noise.shaders`
module and three CI jobs in a second.
