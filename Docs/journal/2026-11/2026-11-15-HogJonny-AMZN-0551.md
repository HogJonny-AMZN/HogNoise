### The GPU port, built
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)
**Board:** [`2026-11-01-gpu-fast-track`](../../plan/board/2026-11-01-gpu-fast-track.md)

The aim is the most modern FastNoise in every language it can run in, each checked against the same vectors. This was
the first language that is not Python: every HogNoise noise as one WGSL shader on wgpu, chosen only by name, judged by
a tolerance measured rather than guessed.

The first question was whether GitHub's runners have a GPU at all. They do not, but both found a software one on their
own, WARP on Windows and Mesa's llvmpipe on Ubuntu, so CI checks the port on every push. From there the shader grew
feature by feature, each held to the CPU at 1e-4, coordinate-scaled, and each shown able to fail by breaking one
constant on purpose. Most of it agreed with the CPU to about 1e-6; cell values and white noise agreed bit for bit.

Three things did not go as planned. Grid cases sit on the lattice, where classic Simplex and OpenSimplex2 choose a
corner on a tie that float32 and float64 round apart, so a handful of points jump; the CPU's own value jumps as much
when a coordinate moves one ulp. @HogJonny-AMZN chose a discrete rule for them rather than a continuous one a hundred
times looser. Then WARP got the single domain warp wrong, by a different count on every run: not rounding but its
compiler, so the shader runs that warp as a loop of one. And the measured rules first failed the very adapter that
measured them, twice: a rounding helper that rounded 0.9999999999999998 up to 1.0, and then, on CI's llvmpipe, a
bit-exact case judged against a correlation of exactly 1.0 that `np.corrcoef` does not always give for identical
arrays. @HogJonny-AMZN capped a derived correlation at 0.999; precision is held by the rule's own tight bound.

The tolerance file now holds 125 rules from four adapters measured at one commit, and all 368 hog cases pass it on
each. The deliberate review then found what the tests had not: a mistyped folder made the measurement tool overwrite
the committed tolerance with zero rules, and the GPU took axes of unequal length without complaint. Both are refused
now, with the other findings, and the rules re-derive byte for byte. Stage 3, HLSL and GLSL generated from this
shader, is next.
→ [PR #22](https://github.com/HogJonny-AMZN/HogNoise/pull/22)

### numpy 2, asked about and iceboxed
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)
**Board:** [`2026-11-15-numpy-2-modernisation`](../../plan/board/2026-11-15-numpy-2-modernisation.md)

During the GPU port @HogJonny-AMZN asked what a numpy 2.5+ port would look like. The answer changed the question: the
1.26 floor stays for the DCC hosts, so modern numpy is a rung beside `vectorized.py`, not its replacement, and the one
option that needs numpy 2, the array API standard, is about running on other people's tensors, not about speed. The two
that do not need it, uint32 hashing and free threading, speed the 1.26 path. Asked, @HogJonny-AMZN said both paths
are maintained: the 1.26 one is what the current project needs, and a 2.5+ one would be future-proofing. So it is an
Icebox row whose first step is a rung comparison, said after the port merged so it stayed out of that branch.

### Stage 3's spec: what naga actually writes
**By:** @HogJonny-AMZN · **Agent:** Claude Code (claude-opus-5-5)
**Board:** [`2026-11-01-gpu-fast-track`](../../plan/board/2026-11-01-gpu-fast-track.md)

@HogJonny-AMZN said go on stage 3, the emitted languages, to review later. The design had assumed naga's other
languages come out usable; running it on the real shader showed two of four do not as they stand. HLSL does: one
file, every entry point compiling in both FXC and DXC, registers one to one with the WGSL bindings. SPIR-V writes
cleanly. GLSL writes, one file per entry point, but with no binding numbers, so a host binds by naga's generated
names. Metal writes with every resource on a fake binding, and naga's command line has no way to give it a map. So
the spec ships HLSL, GLSL and SPIR-V, and makes Metal the owner's decision rather than a given. The other surprise
was a version skew: the naga on this machine is 30.0.1, the one inside the `wgpu` the rung pins is 29.0.1.

The probes, at `989ff6b`, from a scratch directory (`W` the path of `noise.wgsl`):

```text
naga --version                                   # 30.0.1
naga $W out.hlsl out.metal out.spv               # 133,801 / 138,354 / 113,252 bytes, no error
naga --profile core430 --entry-point <ep> --shader-stage compute $W <ep>.comp   # all five; core450 and es too
naga --shader-model 50 $W sm50.hlsl              # byte-identical to the default HLSL
fxc -T cs_5_0 -E <ep> out.hlsl                   # all five entry points, rc 0 (Windows SDK 10.0.18362)
dxc -T cs_6_0 -E <ep> out.hlsl                   # all five, rc 0, warnings only
grep -c "user(fake0)" out.metal                  # 31
grep -c "binding *=" <ep>.comp                   # 0 in every GLSL file
wgpu.backends.wgpu_native.__version__            # 29.0.1.1, whose Cargo.toml pins naga 29.0.1
```
→ [the spec](../../superpowers/specs/2026-11-15-emitted-languages.md)
